HTTP 协议说明

前台提交数据 → JSON 格式 → 后端（以 Dify 工作流为例）· 面向零基础读者

1.最基本的通信模型

HTTP 就是浏览器（客户端）和服务器之间「一问一答」的通信规则。你在网页上点一个按钮、刷新一个页面，背后都是浏览器发出一个「请求」，服务器处理后返回「响应」，浏览器拿到结果渲染给你看。

2.请求与响应的组成结构

请求和响应的结构是对称的，都是「第一行说明情况 + 头部附加信息 + 空行 + 正文数据」：

  • 请求行 / 状态行：请求行说「我要做什么」（如 POST /v1/workflows/run）；状态行说「结果怎么样」（如 200 OK 表示成功）。
  • Headers（头部）：附加说明信息，比如数据格式、身份验证，用户看不到，是「幕后」信息。
  • 空行：分隔符，告诉对方「头部说完了，接下来是正文」。
  • Body（正文）：真正要传输的数据内容。

3.常见请求方法与状态码

请求方法放在请求行里，说明这次通信「想干嘛」：

方法作用举例
GET向服务器「要」数据打开一个网页
POST向服务器「提交」数据登录、发起工作流
PUT更新已有数据修改用户资料
DELETE删除数据删除一条记录

状态码放在状态行里，让你一眼看懂结果：

状态码含义
2xx成功了，如 200 OK
4xx你这边请求有问题，如 404 找不到、401 未授权
5xx服务器那边出错了，如 500

4.实战：前端提交 JSON 到 Dify 工作流

把上面的知识套到实际场景：前端把要提交的数据组织成 JSON，通过 POST 方法发到 /v1/workflows/run 接口，后端（Dify 工作流引擎）接收并执行工作流，再把结果以 JSON 返回。

4.2streaming 模式：SSE 事件流

当 response_mode 设为 streaming 时，前后端之间维持一条 SSE 长连接，后端不是等工作流跑完才一次性返回，而是每到关键节点就推送一条事件：

  • workflow_started —— 工作流开始执行
  • node_started / node_finished —— 每个节点开始和结束时各推一条，可以有多次
  • workflow_finished —— 整个工作流跑完，携带最终结果
对比来看：blocking 模式简单——前端发出请求后一直等，直到后端把整个工作流跑完，一次性返回完整 JSON 结果；streaming 模式体验更好——前端可以像打字机一样边收边渲染，但实现上要多处理 SSE 事件流。
