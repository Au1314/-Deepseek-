# 以项目经理 & 产品验收人视角评审《移动端前端实现规划 V1.0》

> 评审对象：《糖尿病预治智能助手-移动端前端实现规划》V1.0
> 评审人立场：软件项目经理 + 产品验收人
> 评审日期：2026-07-08

---

**总评**：规划的骨架清晰、组件划分和迭代节奏基本合理，能看出对文档做了整体梳理。但作为一份要交付到实训评审、并指导 8 天开发的方案，它**与既有 6 份需求 / 设计文档存在多处一致性缺口，且遗漏了实训项目的一些"硬性教学目标"**。以下按优先级列出问题与整改要求。

---

## 🔴 P0 · 与既有需求 / 设计文档冲突（必须修正）

### 1. PC 端 vs 移动端的**范围变更未被明确说明**

- **依据**：SRS 3.1 明确要求"适配 1920×1080 及以上 PC 分辨率"、"1366×768 可正常浏览"；概要设计 3.1 的界面清单及详细设计 4.4 的管理员模块都是 **PC 布局**（侧边栏+表格）。
- **问题**：客户临时要求"移动端形式展现"，规划直接照做，但没有提交**需求变更说明**——原 SRS 与新形态之间的取舍（如放弃 PC 后台？多端一套还是分端？）未澄清。
- **整改**：在规划前置一节《需求变更与范围说明》，明确"面向 C 端普通用户走 H5，管理员后台保留 PC 版但本次不实现" 之类结论，并按变更管理流程请客户签字。

### 2. **文件命名违反详细设计 §1.1 的规约**

- **依据**：详细设计规定 HTML 用连字符：`risk-prediction.html`、`consult-doctor.html`、`ai-assistant.html`、`life-plan.html`。
- **问题**：规划里改成了 `risk.html`、`consult-chat.html`、`assistant.html`、`plan.html`——**擅自更改命名规约**，会导致测试用例、CodeArts 任务卡、需求跟踪矩阵全部对不上。
- **整改**：按详细设计原文件名回退，所有 URL / 任务卡 / 测试脚本保持一致。

### 3. **管理员 & 医生角色被完全省略**

- **依据**：SRS §1.3 明确列出三类角色，§2.11 有管理员模块（用户管理 UC-016、内容审核 UC-017），FR-016/FR-017 已进跟踪矩阵。
- **问题**：规划只做了普通用户端，管理员端一字未提，也没解释是"后续版本"还是"本次剔除"。
- **整改**：至少写清"管理员模块采用 PC 端另建，不在本 H5 工程内"，或提供最小可行的管理员移动端方案。

### 4. **数据字典与 SRS 字段不一致，规划直接跳过**

- **依据**：SRS 要求注册字段含手机号+邮箱+验证码+昵称+性别+年龄；数据字典 `users` 表只有 `user_id / username / password / avatar_url`。风险等级在 SRS 是"低/中/高"，`user_risk_info` 只存 `message`+`disease`。
- **问题**：规划没有识别并调解这个矛盾，D2 一联调必定卡壳。
- **整改**：新增《字段对齐表》一节，逐字段标注"以数据字典为准 / 以 SRS 为准 / 需扩表"，本次实训范围以哪份为准要写死。

### 5. **打卡数据模型与 UI 分类不匹配**

- **依据**：数据字典 `punch_in.punch_type` 只允许"饮食/运动"；血糖走 `check_in_records`，用药走 `medication_records`，体重无独立表。
- **问题**：规划画的打卡 UI 是 5 类 Tab 平铺，把 3 张表混成一个表单。前端提交后不知道往哪张表写。
- **整改**：要么把 UI 改为"生活打卡（饮食/运动）+ 体征记录（血糖/血压/体重）+ 用药记录"三个入口对应三张表；要么补充表结构变更申请。

### 6. **"名医在线"实为 AI 医生，措辞误导**

- **依据**：数据字典 `doctor_information.chat_token` 是 **Dify Chatflow 授权 Token**，没有 doctor 用户登录体系。
- **问题**：规划继续沿用 SRS 里"医生登录审核回复"的描述，会让验收人误以为要做医生工作台。
- **整改**：明确写"名医对话 = 预设人设的 AI 医生角色扮演，走 Dify Chatflow，不涉及医生真人账号"。

## 🟠 P1 · 实训教学目标缺失（会直接扣分）

### 7. **未安排 MasterGo 原型 / 低保真阶段**

- **依据**：项目说明 §4 明确"UI 界面设计阶段使用 MasterGo AI 工具"，产出低保真+高保真原型；实训环节表也把原型放在编码前。
- **问题**：规划直接从 D1 环境搭建到 D3 首页开工，跳过了原型评审这一教学关键环节。
- **整改**：在 D1 前追加"D0：MasterGo 出全 15 屏低保真 + 高保真，评审通过后再进入编码"。

### 8. **CodeArts / DevOps 全流程缺席**

- **依据**：项目说明和 SRS 都强调 CodeArts 项目工程、代码托管、迭代规划、甘特图。
- **问题**：规划的目录里没有 `.codearts`、README、CI 配置；开发计划里也没写"每日提交/迭代评审/需求跟踪矩阵回填"。
- **整改**：加一节《DevOps 与协作》说明代码仓、迭代命名、任务卡对应 FR-xxx、每次合入触发流水线。

### 9. **AI 辅助编程工具使用规范缺失**

- **依据**：项目说明明确"编码阶段—前端开发：DeepSeek + Cline 辅助编程"、"测试阶段：DeepSeek 生成 Playwright 脚本"。
- **问题**：规划没有交代团队如何统一 Prompt、代码 review 规范、AI 生成代码的验收标准——这是实训**核心考核点**。
- **整改**：补一节《AI 编程约定》：Cline Prompt 模板、代码风格提示词、AI 生成代码必须走一次 code review。

### 10. **测试计划过于单薄**

- **依据**：SRS §3.2 要求 200 并发、AI 8 秒响应；概要设计 §6 要求分层异常；实训"项目部署与测试"占 4 学时且必须自动化。
- **问题**：规划只在末尾提一句 Playwright 覆盖黄金链路；缺测试用例设计、性能验证方法、缺陷跟踪。
- **整改**：新增《测试策略》：单元/UI 自动化/性能/兼容性四层，用例编号对齐 FR，DeepSeek 生成用例 → Playwright 脚本 → 报告归档。

### 11. **需求跟踪矩阵未回填**

- **依据**：SRS 附录 B 提供了 FR-001~FR-017 跟踪矩阵。
- **问题**：规划的 8 天迭代表用的是"首页/风险预测/生活方案"这种业务名，没和 FR 编号绑定，验收时无法逐条打勾。
- **整改**：在每个迭代任务后括号标注对应的 FR 编号，例如 "D4 风险预测 (FR-004/005/006/007)"。

## 🟡 P2 · 专业性与用户体验缺口（建议改进）

### 12. **数据安全 & 合规风险未标记**

数据字典 `password` 明文；SQL 通过自然语言拼接（`查询用户名为${u}密码为${p}`）存在 **Prompt 注入 / 命令注入**风险；`chat_token` 直接存 `localStorage`。SRS §3.3 §6.1 要求加盐哈希、HTTPS、最小化收集。规划里对这些**一个字都没提**，作为验收人无法通过合规检查。

- **整改**：新增《安全 & 合规》一节，至少写清
  - (a) 密码前端 SHA-256 预哈希 + 后端加盐；
  - (b) 用户输入做转义再拼 Prompt；
  - (c) Token 用 sessionStorage / 内存 Map，退出即清；
  - (d) HTTPS 与 CSP 策略。

### 13. **目标用户特征未反映在设计中**

- 用户群包含"糖尿病患者、高危人群"——**中老年占比高**。规划正文字号 14、组件圆角小、密度高，不友好。
- **整改**：主字号提升到 16，提供"长辈模式"字号切换；关键数字（血糖值、风险分）加大字号加粗；对比度符合 WCAG AA。

### 14. **移动端落地细节缺失**

- iOS Safari `100vh` bug、软键盘弹起遮挡输入框、`env(safe-area-inset-bottom)` 底部安全区、下拉刷新与 iOS 橡皮筋冲突——规划均未提。
- 桌面端"手机壳"外的大片留白也没有利用（可放演示说明、切换用户、扫码到手机）。
- **整改**：在《手机外壳样式方案》后追加《移动端适配踩坑清单》并给出对策；PC 外壳外补一个"演示面板"提升评审展示效果。

### 15. **信息架构没有做取舍论证**

- 顶层功能 8 项被压到 5 项 TabBar，"AI 助手"凸起的正当性、"生活方案"进 TabBar 而"风险预测"退到宫格——这些取舍**没有依据**，可能被产品评审质疑。
- **整改**：补一段用户任务频次分析（每天打卡 vs 每周方案 vs 一次风险预测），用数据说明为什么把打卡/方案放 TabBar。

### 16. **D8 排期过载**

- D8 一天塞了打卡表单、打卡分析（含 ECharts）、资讯列表、资讯详情、糖尿病类型、个人中心、全链路联调——**至少 3 天的工作**。
- **整改**：把资讯 / 糖尿病类型 / 个人中心提前分散到 D3~D7 的下午作为缓冲任务；D8 只留联调与回归。

### 17. **前后端联调节奏未定义**

- Dify 工作流由谁搭？何时提供 mock？规划里 D2 就要联调登录，但工作流开发进度无描述。
- **整改**：在《DevOps 与协作》里画一张前端 vs Dify vs 数据 三条泳道的时间线，标出契约冻结日和联调日。
